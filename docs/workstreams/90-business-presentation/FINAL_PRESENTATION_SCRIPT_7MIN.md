## 발표 대본

### 0:00–0:15 — Cover

> 안녕하십니까. SPECTRA는 위성 전자부품 검토에 필요한 임무 조건, 부품 정보, 방사선 시험 자료를 한 흐름에서 대조하는 검증 플랫폼입니다. 흩어진 자료를 연결해 무엇을 확인했고 무엇이 더 필요한지 명확하게 보여줍니다.

### 0:15–0:40 — 01 · Radiation & Shielding Basics

> 우주 방사선은 전자부품에 누적선량인 TID와 순간적인 단일사건 영향을 일으킬 수 있습니다. 알루미늄 차폐는 누적 피해를 줄이지만 단일사건 오류와 파괴 위험까지 없애지는 않습니다. SPECTRA는 TID와 SEU 예상 사건 수를 계산하고, SEL·SEB·SEGR 같은 파괴성 SEE는 정확한 부품의 시험 근거가 있는지 별도로 확인합니다.

### 0:40–1:05 — 02 · COTS in Space

> COTS는 산업용 시장에서 쉽게 조달할 수 있고 실제 위성에도 쓰입니다. 하지만 지상에서 잘 작동했다는 사실만으로 우주 방사선 환경에서도 안전하다고 판단할 수는 없습니다. SPECTRA는 임무 기간, 방사선 환경과 차폐 조건을 이용해 부품이 견뎌야 할 누적 방사선량인 TID와 순간 오류인 SEU의 예상 횟수를 계산합니다. 이어 제조사·부품번호·공정·로트가 시험 대상과 같은지, SEL·SEB·SEGR처럼 부품을 손상시킬 수 있는 단일사건 시험까지 갖춰졌는지 확인합니다.

### 1:05–1:30 — 03 · The Evidence Gap

> 위성 부품을 검토하려면 임무 방사선 환경, 부품 명세, 방사선 시험 결과와 검토 기준을 함께 봐야 하지만 이 자료들은 서로 다른 문서에 흩어져 있습니다. 오른쪽의 세 질문처럼 시험받은 부품과 사용할 부품이 같은지, 시험 조건이 현재 임무와 맞는지, 필요한 시험 범위가 모두 갖춰졌는지를 확인해야 합니다. 현재 확보한 공개 COTS 자료도 승인 대상과 시험품의 패키지가 다르고 로트 정보가 없어 직접 비교할 수 없습니다.

### 1:30–2:05 — 04 · Evidence-Backed Customer Pain

> 이 부담은 저희만의 추측이 아닙니다. NASA 자료는 CubeSat 팀의 예산·일정 제약과 분산된 COTS 데이터를, 미국 정부감사원 GAO는 로트 편차·단종·추적성 위험을, 유럽우주국 ESA는 구성관리와 감사 부담을 보여줍니다. SPECTRA는 빠진 근거와 재검토 지점을 승인 전에 찾고 다음 행동을 반환합니다. 실제 시간 절감 효과와 구매 의향은 앞으로 사용자 조사로 확인해야 합니다.

### 2:05–2:30 — 05 · Conventional Review Workflow

> ESA는 대형 우주 프로젝트의 기술·관리 정보가 수만 건의 문서로 관리되어 왔고, 최신 Digital Spacecraft 방향에서는 이를 자동화되고 추적 가능한 흐름으로 전환한다고 설명합니다. 현재 검토자는 환경 모델, BOM, 시험 원문과 승인 이력을 다시 대조합니다. SPECTRA는 이 연결을 기계가 확인할 수 있는 데이터 규칙과 근거 체인으로 바꿉니다.

### 2:30–2:55 — 06 · SPECTRA · Evidence to Decision

> SPECTRA의 입력은 세 가지입니다. 임무 기간·환경·차폐 조건, 제조사·부품번호·공정·로트 같은 정확한 부품 정보, 그리고 TID·SEU·파괴성 단일사건 영향 시험 결과입니다. 세 역할은 이 자료의 연결 상태를 확인합니다. 현재 모델로 직접 비교할 수 없는 시험 조건은 맞는다고 추정하지 않고, 판단을 멈춘 위치와 이유, 확인해야 할 다음 행동을 반환합니다.

### 2:55–3:15 — 07 · Decision Boundary

> 지원 범위는 근거 연결, 감사 가능성, 결정론적 실행과 fail-closed 판단입니다. 임무 인증이나 가속기 시험을 대신하지 않고, 생성형 AI가 빈칸을 채워 승인하지도 않습니다. 필수 근거가 빠지면 승인 결론은 보류하되, 이미 들어온 자료에서 확인 가능한 항목은 끝까지 검사해 완료·불일치·추가 입력으로 나눕니다.

### 3:15–3:40 — 08 · GCP Multi-Agent Execution

> GCP에서는 하나의 Workflow 실행 안에서 Mission·Parts·Assurance 세 비공개 Agent가 역할을 나눠 검증합니다. Mission은 환경과 출처, Parts는 부품과 시험, Assurance는 정책과 결측을 확인합니다. 같은 저장 객체 버전과 입력 해시, 배포 버전을 고정하고 실행 이벤트를 하나의 감사 기록으로 남깁니다.

### 3:40–4:10 — 09 · Integrity by Design

> 안정성은 공격 횟수보다 틀린 입력이 승인으로 넘어가지 않는 구조에서 만듭니다. 스키마를 먼저 검사해 잘못된 입력을 계산 전에 거절하고, 결정론적 Core만 수치를 계산합니다. 제조사·부품번호·공정·로트가 같은지, 같은 입력을 같은 규칙으로 정리해 만든 해시인지, 오류가 항상 같은 코드로 닫히는지를 확인합니다. Agent는 비공개 배포 경계 안에서 실행하며, 근거가 빠지거나 서로 맞지 않으면 확인된 항목과 미확인 항목을 분리하고 최종 판단만 보류합니다.

## 4:10–6:10 — Evidence Console 시연

### 4:10–4:45 — 문서 1개 검사

**조작:** 미리 연 Cloud Run `Evidence Console`로 전환 → `문서 1개 검사` → `합성 비정형 PDF 예시 실행`.

> 이 4쪽 합성 PDF는 표, 다단 본문, 차트와 각주가 섞인 시험 보고서입니다. 서버가 실제 PDF를 읽고 원본 hash를 만든 뒤 부품 식별 정보와 TID·SEE 항목을 원문 위치와 함께 후보로 냅니다. 화면의 7 대 7은 고정된 합성 정답과 후보 집합이 일치했다는 뜻이지, 일반 문서 정확도나 과학적 보증 100퍼센트를 뜻하지 않습니다.

> 후보를 모두 찾았어도 승인 BOM target과 실제 시험 조건·임무 적용성이 없기 때문에 최종 판단은 보류됩니다. 하지만 이미 확인 가능한 주문형번과 제조사 문자열은 계속 검사합니다. 오른쪽의 확인 완료·불일치·추가 입력 수와 함께, 어느 역할에서 왜 보류했고 무엇이 더 필요한지 보여줍니다.

### 4:45–5:35 — 3개 입력 연결

**조작:** `3개 입력 연결` 메뉴 선택 → `1 · 여러 문서 근거 연결 실행` → `2 · 조건 변경 영향 확인`을 차례로 클릭.

> 첫 번째는 구조화된 합성 임무 자료 세 건을 실제 결정론적 Core에 넣습니다. 같은 부품인지 여섯 식별 필드를 대조하고 TID·SEU를 계산하며, TID·SEU·SEL·SEB·SEGR 근거가 어느 문서에 있는지 연결합니다. 다만 현재 모델이 직접 비교하지 못하는 시험 조건은 맞는다고 추정하지 않아 최종 판단은 HOLD입니다.

> 두 번째는 무엇이 바뀌면 어디까지 다시 검토해야 하는지를 보여줍니다. 임무 기간 변경은 TID와 SEU, 차폐 변경은 현재 모델상 TID를 다시 계산하게 하고, 부품번호 변경은 다섯 사건의 기존 근거 연결을 모두 무효화합니다. 이 범위와 다음 행동도 규칙 기반으로 반환합니다.

### 5:35–6:00 — 공격 검증 기록

**조작:** 같은 콘솔에서 `공격 검증 기록` 메뉴 선택 → `저장된 공격 검증 결과 보기` 클릭.

> 이 화면은 새 실행이 아니라 독립 확인 후 저장한 합성 GCP 기록입니다. 정상 실행에서 세 Agent는 모두 VALID이고 Workflow도 성공했지만 실제 환경과 부품 시험 근거가 없어 최종 판단은 HOLD입니다. 입력 body hash가 다르면 첫 단계에서 멈추고, 승인되지 않은 endpoint는 Agent 호출 전에 차단합니다. 실행 성공과 방사선 보증을 분리한 것이 핵심입니다.

## 절대 넘지 않는 주장 경계

- 실제 environment contract: 0건
- 승인 BOM 기반 exact-part evidence: 0건
- 현재 PDF parser: Cloud Run/로컬 동일 `pypdf`; OCR·Document AI·Gemini 호출 없음
- GCP 화면: 저장된 합성 snapshot; live 조회·실행 아님
- 합성 `7 / 7`: 고정 control의 exact candidate 비교이며 일반 정확도·과학 보증 수치 아님
- 침투시험·보안 인증·실제 방사선 assurance 완료를 주장하지 않음
- 비용 절감·ROI·구매 의향은 아직 측정하지 않음
- 구매자·예산 책임자·도입 방식은 아직 검증하지 않음
- 사람 팀의 역할·협업 성과는 확인된 사실이 없어 발표 주장으로 만들지 않음; Mission·Parts·Assurance는 시스템의 증거 책임 분리임

## 시연 실패 fallback

- 문서 검사가 실패하면 새 값을 만들지 않고 저장된 화면 또는 말로 `최종 판단 보류 · 승인 대상과 실제 시험 조건 보완 필요`만 설명한다.
- GCP snapshot이 열리지 않으면 저장된 결론만 말한다: `정상 실행도 실제 근거 0이라 HOLD · body hash 불일치는 조기 차단 · endpoint override는 Agent 호출 전 차단`.
- 실패를 숨기거나 임의의 성공 화면·수치·receipt를 만들지 않는다.

## 3분 Q&A용 짧은 답변

**COTS라면 차폐 없이도 쓰는 부품 아닌가?**

지상에서는 해당 사용 환경에 맞춰 일반적으로 사용합니다. 우주에서는 방사선·진공·열주기 등 임무 환경이 달라 차폐와 완화 설계, 정확한 부품 시험 근거를 함께 검토하며, 차폐만으로 모든 SEE가 해결되지는 않습니다.

**왜 Multi-Agent인가?**

답을 여러 개 만들기 위해서가 아니라 Mission·Parts·Assurance의 증거 책임과 실패 위치를 분리하기 위해서입니다. 한 단계가 실패하면 다음 단계가 빈칸을 추측하지 않고 멈춥니다.

**공격 검증은 왜 공개 화면에서 live로 실행하지 않나?**

문서 검사와 Core 검증은 요청할 때마다 실행합니다. 공격 검증은 공개 데모에 Workflow 실행·Storage 쓰기 권한을 열면 누구나 반복 호출해 비용과 로그를 발생시키고 내부 경계를 탐색할 수 있어, 독립 확인한 실행 ID·감사로그·결과 snapshot을 보여줍니다. 실행할 수 없어서가 아니라 데모 읽기 권한과 운영 쓰기 권한을 분리한 설계입니다.

**실제 데이터를 썼나?**

현재 본 시연은 합성 PDF와 저장된 합성 GCP 기록입니다. 실제 후보 문서를 로컬에서 읽는 경로는 있지만 권리·승인 BOM·시험 조건·임무 적용성이 닫히지 않아 판단에는 사용하지 않았습니다.

**AI가 계산하거나 승인하나?**

아닙니다. 핵심 계산과 최종 gate는 결정론적 Core가 담당하고, AI는 향후 원문 위치가 붙은 후보 추출을 보조합니다. SPECTRA는 자동 승인하지 않고 부족한 근거와 다음 행동을 표시하며, 최종 판단은 조직이 지정한 기술 검토자가 담당합니다.

**reviewer와 owner는 누구인가? 승인 인계는 어떻게 하나?**

개인 이름이나 현재 확정된 사용자가 아니라 결측을 해결할 조직 역할입니다. owner는 시험·BOM·임무 조건 같은 부족한 근거를 보완하고, reviewer는 그 근거와 적용성을 검토해 최종 판단합니다. 실제 운영 계약이 없으므로 현재 UI에는 임의의 담당자·승인 상태·receipt identity를 만들지 않았습니다.

**누가 구매하고 어떻게 도입하나?**

소형위성 개발팀, 부품 공급망, 시험기관, 품질·미션 보증 조직의 문제는 공식 자료로 확인했지만, 구매자·예산 책임자·도입 방식·지불 의향은 아직 검증하지 않았습니다. 현재는 제품 동작과 문제 근거까지만 주장합니다.

**팀 시너지는 무엇인가?**

사람 팀의 구성과 협업 성과는 확인된 사실이 없어 만들지 않습니다. 발표에서 말하는 Mission·Parts·Assurance는 서로 다른 답을 생성하는 팀원이 아니라 시스템 내부의 증거 책임과 실패 위치를 분리한 역할입니다.

**보안과 방사선 보증이 끝났나?**

아닙니다. 입력 계약, hash, 결과 결속과 GCP 실행 경계의 fail-closed 동작을 확인했습니다. 실제 데이터 교차검산, 침투시험, 운영 권한과 서명 체계는 남아 있습니다.
