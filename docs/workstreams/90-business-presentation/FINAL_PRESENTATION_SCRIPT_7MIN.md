# SPECTRA 최종 발표 대본 — 약 7분

> 현장에서는 문장을 전부 외우기보다 굵은 흐름을 기억한다. 모든 방사선 수치는 합성 데모이며, 실제 환경·승인 BOM·시험 원문이 없어 최종 판단은 `HOLD`다.

## 0:00–0:15 표지

“안녕하세요. SPECTRA는 우주 방사선 계산 결과와 그 판단 근거를 연결하는 의사결정 시스템이다. 오늘 보여 드릴 수치는 합성 데모 데이터이며, 실제 방사선 보증 결과는 아니다.”

## 0:15–0:45 화면 1 — 문제

“우주 부품 검토의 문제는 계산식 하나가 없는 것이 아니다. 환경 모델 출력, 부품 목록, 시험 문서가 서로 다른 파일과 조직에 흩어져 있어, 계산 결과가 어떤 근거에서 나왔는지 연결이 끊기기 쉽다는 점이다. SPECTRA는 계산만 보여 주는 대신 입력부터 근거와 최종 판단까지 한 흐름으로 남긴다.”

## 0:45–1:10 화면 2 — 임무와 BOM

“먼저 어떤 임무에서 어떤 부품을 검토하는지 고정한다. 여기서는 고도 550킬로미터의 1년 저궤도 임무와 합성 메모리 부품을 사용한다. BOM은 실제 제작에 들어갈 부품 목록이다. 같은 이름의 부품이라도 제조 공정과 로트가 다르면 방사선 특성이 달라질 수 있어 정확한 식별이 필요하다.”

## 1:10–1:45 화면 3 — 환경과 차폐

“차폐 두께를 고르면 엔진이 미리 검증한 고정 결과를 불러온다. TID는 임무 동안 반도체에 누적되는 방사선량이고, krad(Si)는 실리콘 기준 누적선량 단위다. 설계계수 2는 계산값의 두 배를 요구량으로 보는 여유 계수다. 현재 합성 모델은 1, 2, 3, 4밀리미터만 지원하므로 5밀리미터는 임의로 보간하거나 외삽하지 않고 계산을 멈춘다.”

## 1:45–2:15 화면 4 — 부품 증거

“좋은 숫자와 충분한 증거는 같은 말이 아니다. 합성 fixture로 TID와 SEU 계산 경로는 실행할 수 있지만, 실제 부품을 승인하려면 정확한 부품의 시험 원문과 조건, 공정, 로트, 사용 권리가 필요하다. 이 근거가 없기 때문에 화면은 계산 결과가 있어도 실제 적합성을 주장하지 않는다.”

## 2:15–2:45 화면 5 — ECC

“SEU는 입자 하나가 메모리 값을 뒤집는 단일사건 오류다. ECC는 그중 수정 가능한 오류를 찾아 고쳐 임무 중 남는 논리 오류를 줄인다. 현재 Core 결과에서 원래 SEU는 0.063072이고 ECC 적용 후 잔여값은 0.013072다. 다만 이는 합성 비교일 뿐 실제 부품의 ECC 성능을 보증하지 않는다.”

## 2:45–3:20 화면 6 — 신뢰성 원칙

“SPECTRA의 신뢰성은 네 가지 원칙으로 설명할 수 있다. 같은 입력과 버전이면 같은 결과를 내고, 지원하지 않는 범위는 추정하지 않는다. 실제 근거가 없으면 낙관적으로 승인하지 않고 HOLD하며, Core가 만든 결과와 Product에 도착한 값이 다르면 그 숫자를 숨긴다. TMR이나 watchdog 같은 전자장비 제어를 구현한 것이 아니라, 우리가 다루는 계산·증거·판단 과정의 신뢰성을 지키는 범위다.”

## 3:20–4:10 화면 7 — Multi-Agent와 GCP

“이 책임을 하나의 AI에게 모두 맡기지 않았다. Mission Agent는 임무 입력과 Core 계산 결과의 무결성을 확인한다. Parts Agent는 정확한 부품 식별과 시험 근거를 확인한다. Assurance Agent는 앞선 두 결과를 독립적으로 대조하고 최종 HOLD를 유지한다. GCP Workflows가 이 호출 순서와 실패 경로를 관리하고, 세 Agent는 각각 분리된 Cloud Run 서비스에서 실행된다. Storage는 입력과 결과를 보존하고 Logging은 같은 실행의 감사 기록을 남긴다. 정상 합성 실행에서도 실제 근거가 없으므로 세 Agent는 처리를 완료하지만 최종 판단은 HOLD다.”

## 4:10–4:50 Product 화면 1·2 — 실제 사용 흐름

“Product에서는 임무와 부품을 확인하고 차폐와 ECC 조건을 바꿔 결과 차이를 볼 수 있다. 5밀리미터처럼 모델 범위를 벗어나면 값을 만들지 않는다. 중요한 점은 UI가 새 물리 계산식을 갖는 것이 아니라, 검증된 Core 결과를 그대로 읽고 설명한다는 것이다.”

## 4:50–5:20 Product 화면 3 — 보증 판단

“이 화면은 확인된 것, 아직 필요한 것, 그래서 내린 결정, 다음 행동을 분리한다. 합성 계산 재현과 범위 차단은 확인했다. 그러나 실제 환경 출력, 승인 BOM과 시험 원문, 독립 검토가 아직 필요하다. 그래서 HOLD는 실패나 불합격이 아니라 현재 근거로는 승인하지 않는 안전한 상태다.”

## 5:20–6:05 Product 화면 4·GCP Console — 실행 증거

“여기서는 설계 그림이 아니라 실제 GCP 실행 snapshot을 보여 준다. 콘솔 상단의 초록색 성공은 Workflow가 오류 없이 끝났다는 뜻이지 방사선 보증 PASS가 아니다. 아래 출력의 `result.agent_results`에서 mission, parts, assurance 세 결과를 확인할 수 있고, 같은 출력의 `result.assurance_decision`이 `HOLD`인지 확인할 수 있다. 즉 세 역할이 실제로 호출되어 결과를 남겼고, 근거가 부족하다는 안전 판단도 유지됐다.”

## 6:05–6:45 Product 화면 5 — 결과 전달 무결성

“마지막으로 계산 뒤의 전달 오류를 재현한다. Core의 정상 기록은 0.013072다. 원본을 보존한 테스트용 사본에서 이 숫자 하나만 0.013073으로 바꾼다. 대조 전에는 아직 판단하지 않고, Core 기록과 비교해 다르다는 것을 확인하면 도착 숫자를 숨기고 HOLD한다. 이것은 해킹 전체를 막았다는 주장이 아니라 계산 결과가 Product까지 같은 값으로 전달됐는지 확인하는 안전장치다.”

## 6:45–7:00 가치·한계·마무리

“SPECTRA의 가치는 더 그럴듯한 숫자를 만드는 것이 아니라, 어떤 입력과 근거로 계산했고 무엇이 부족해 결정을 보류했는지 추적 가능하게 만드는 데 있다. 다음 단계는 실제 환경 모델 출력과 승인 BOM·시험 원문을 연결하고 같은 규칙으로 다시 검토하는 것이다. 계산 가능한 것과 승인 가능한 것을 구분하는 것, 이것이 SPECTRA의 핵심이다.”

## GCP Console에서 딱 볼 곳

1. 상단 `실행 상태: 성공`: Workflow가 끝까지 실행됐다는 증거다. 방사선 PASS가 아니다.
2. 왼쪽 아래 `출력` JSON의 `result.agent_results`: 그 안의 `mission`, `parts`, `assurance`가 세 Agent 결과다.
3. 같은 `result` 안의 `assurance_decision: "HOLD"`: 최종 판단이다.
4. 시간이 없으면 오른쪽 복잡한 흐름도는 확대하지 않는다. 출력 JSON의 위 두 지점만 보여 주고 Product 화면으로 돌아온다.
