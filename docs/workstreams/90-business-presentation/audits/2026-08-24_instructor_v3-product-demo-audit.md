## 2. 비전문가가 30초 안에 이해하는 한 문장

> **SPECTRA는 AI가 우주 부품의 안전성을 대신 판단하는 도구가 아니라, 환경·부품·시험자료가 정말 연결돼 있는지 검사하고 하나라도 부족하면 승인을 멈추는 검토 플랫폼입니다.**

2. 04–08에서 차폐·부품·ECC를 이용해 “좋은 숫자만으로는 승인할 수 없다”는 원칙을 설명한다.
3. 09–10에서 결정론적 Core와 세 Agent의 책임, GCP 저장 실행 기록과 공격 차단을 보여준다.
4. 11에서 Product Demo로 이동해 파일이 어느 관문에서 멈추는지와 설계 변경 시 어디부터 다시 검사하는지를 보여준다.
5. Closing에서 실제 environment contract와 승인 exact-part evidence가 0건이며 최종 HOLD라는 경계로 닫는다.

특히 대본의 Slide 10 설명은 화면과 정확히 맞는다. 저장 기록 1–3만 실행 증거로 다루고, live 실행이나 완전한 보안 검증으로 과장하지 않는다. Product Demo도 실제 PDF에서 식별 후보를 추출했지만 판단에 사용하지 않는다는 차이를 잘 보여준다.

다만 다음 세 연결 문제는 남아 있다.

- Product 화면은 6개 관문을 렌더링하면서 결과 설명에는 “다섯 관문”이라고 적혀 있다. 심사 중 발견되면 검증 체계 자체의 일관성을 의심받을 수 있다.
- 대본의 “세 후보를 차례로 클릭”만으로는 각 결과가 실행되지 않는다. 후보를 바꿀 때마다 다시 `검사 시작`을 눌러야 한다.
- Slide 11은 로드맵 화면이지만 곧바로 현재 Product Demo로 전환한다. “로드맵 중 어디까지 현재 구현됐는가”를 한 문장으로 구분하지 않으면 미래 기능과 현재 기능이 섞여 보일 수 있다.

## 4. 개선 우선순위

### P0 — 제출 전 반드시 해소

1. **현재 변경본으로 브라우저 회귀 실행**
   `실제 후보 3개` 로딩, TI PDF 후보 선택, 5번 관문 HOLD, Step 3 변경 재검사, 처음으로 돌아가기까지 전체 경로를 발표에 사용할 브라우저와 해상도에서 확인해야 한다.

2. **95초 시연 동선 축소 및 실측**
   합성 후보 3개를 모두 실행하지 말고 `변조 자료 1개 → 실제 TI PDF 후보 1개 → ECC 변경 1개`만 남기는 편이 안전하다. 실제 클릭 리허설로 Product 구간이 95초 이내인지 확인해야 한다.

3. **관문 수와 조작 큐 일치**
   Product 화면의 “다섯 관문”을 “6개 관문”과 통일하고, 대본 조작 큐에는 “후보 선택 후 검사 시작”을 명시해야 한다.

### P1 — 점수를 실제로 올리는 개선

1. **구매자와 파일럿 의사결정 기준 명시**
   예: “위성 시스템 엔지니어링 리드가 파일럿 오너이며, case당 active review time·trace completeness·return rate로 도입을 판단한다.”

2. **GCP와 Product Demo의 경계 설명**
   “Product 화면은 같은 fail-closed 규칙을 보여주는 로컬 검토 UI이며, 이 클릭이 Cloud Run Workflow를 새로 실행하는 것은 아니다”라고 한 문장으로 고정하는 것이 좋다.

3. **정적 fallback 준비**
   TI PDF 후보가 5번에서 HOLD되는 화면과 변경 재검사 화면을 각각 한 장씩 준비해야 한다. 오류 시 새 값을 만들지 않는다는 말만으로는 시각적 시연을 대체하기 어렵다.

### P2 — 완성도 개선

1. exact identity, provenance, coverage, receipt 같은 영어 용어는 첫 등장 이후 한국어 중심으로 줄인다.
2. 3단계 장기 로드맵보다 첫 파일럿 고객이 실제로 수행할 한 가지 업무를 더 강조한다.
3. execution ID, revision, stable code 같은 세부 정보는 본 발표보다 Q&A에서 제시한다.

## 5. 7분 안에 자를 내용과 반드시 남길 장면

**자를 내용:** Slide 04의 독립적인 차폐 원리 설명. Slide 06에서 1·4·5 mm를 직접 조작하며 같은 내용을 더 설득력 있게 보여주므로, Slide 04는 한 문장으로 통과하거나 생략해도 서사가 유지된다.

**반드시 남길 장면:** 실제 TI 328쪽 PDF에서 부품번호·제조사·TID 표지를 추출했음에도 5번 ‘시험 적용성’ 관문에서 HOLD하는 장면. 이 장면 하나가 AI 활용, 실제 문서 처리, 할루시네이션 방어, 인간 검토 필요성, 제품 가치를 동시에 보여준다.

## 6. 시연 실패 위험과 fallback

| 위험 | 영향 | 권장 fallback |
|---|---|---|
| 최신 세 번째 후보 경로의 브라우저 회귀 미실행 | 후보가 안 뜨거나 다음 단계가 열리지 않을 수 있음 | 실제 후보 화면을 미리 두 번째 탭에 열어두고, 실패 시 TI 후보 HOLD 캡처로 전환 |
| 후보 변경 후 `검사 시작` 재클릭 누락 | 화면이 ‘검사 전’에 머물러 설명과 불일치 | 합성 후보는 한 개만 실행하고 조작 큐를 키보드 옆에 준비 |
| 로컬 데이터 fetch·embedded fallback·브라우저 보안 차이 | `DATA_UNAVAILABLE · HOLD`만 표시될 수 있음 | 발표에 사용할 동일한 localhost 실행 방식으로 사전 확인; 실패 시 Slide 10 저장 기록으로 fail-closed 원리를 설명 |
| 화면 폭 1080px 미만 또는 확대율 문제 | 오른쪽 결과 패널이나 관문 일부가 잘림 | 발표 해상도와 브라우저 확대율을 고정하고 전체화면 전환을 사전 확인 |
| 95초 Product 구간 초과 | Closing과 증거 경계 설명이 잘림 | 실제 후보 설명을 한 문장으로 줄이고 Step 3은 ECC 한 번만 실행 |

시연 실패 시 사용할 짧은 문장은 다음 정도가 좋다.

> “현재 화면도 실패를 PASS로 바꾸지 않고 `DATA_UNAVAILABLE · HOLD`로 닫았습니다. 준비된 저장 기록에서 보시듯 SPECTRA의 핵심은 오류가 나도 승인값을 만들어내지 않는 것입니다.”

## 7. 예상 심사 질문 5개와 짧은 모범답

### Q1. 왜 하나의 서비스가 아니라 Multi-Agent인가요?

> 숫자를 더 많이 만들기 위해서가 아니라 책임과 실패 경계를 분리하기 위해서입니다. Mission은 환경, Parts는 exact-part evidence, Assurance는 결과와 결측을 독립 대조하며, 한 단계가 실패하면 뒤 Agent는 호출하지 않습니다.

### Q2. 실제로 GCP에서 실행된 것인가요?

> 1–3번은 Workflows와 private Cloud Run Agent 3종을 사용한 독립 확인 저장 실행 기록입니다. 현재 화면 클릭은 새 실행이 아니라 snapshot 재현이며, 4–5번은 실행 기록이 아닌 동작 원리 예시입니다.

### Q3. 실제 TI 문서를 읽었으면 실제 부품을 판단할 수 있지 않나요?

> 아닙니다. 부품번호·제조사·TID 언급을 원문 위치에 묶은 검토 후보일 뿐입니다. 승인 BOM, 시험 조건, 임무 적용성, 파괴성 SEE coverage가 닫히지 않았기 때문에 판단에는 사용하지 않고 HOLD했습니다.

### Q4. 아직 ROI가 없는데 비즈니스 가치는 무엇인가요?

> 현재 절감액을 주장하지 않습니다. 첫 파일럿에서 case당 active review time, trace completeness, 보완 return rate를 측정해 반복 탐색과 재검토가 실제로 줄어드는지 검증하겠습니다.

### Q5. 혼자 만든 프로젝트에서 팀 시너지는 무엇인가요?

> 인원수가 아니라 책임 분리와 독립 검증 구조로 설명할 수 있습니다. Core와 세 Agent가 서로 다른 책임을 가지며, 저장 기록·stable code·공격 테스트로 결과를 재대조합니다. 시너지는 한 모듈의 실패를 다른 모듈이 추측으로 덮지 못하게 하는 구조에서 나옵니다.
