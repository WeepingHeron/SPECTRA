## 2. 발표 중 즉시 감점될 수 있는 주장

1. **“데이터 무결성으로 궤도 방사선 신뢰성을 입증한다.”**
   - 실제 환경·정확 부품 contract가 0건이고 assurance가 `HOLD`이므로 “입증”이 아니다.
   - 권장: “방사선 판단에 필요한 근거가 연결됐는지 검증하고, 부족하면 HOLD합니다.”

2. **“NASA와 ESA 통계상 소형위성의 40~50%가 조기 실패하며 그 원인의 86%가 방사선 취약 전자부품 결함이다.”**
   - HTML도 출처 후보·적용 범위 독립 검증 전으로 표시한다. 특히 86%의 직접 근거가 화면에 없다.

3. **“AP-8/AE-8·SHIELDOSE-2 기반 2 mm 해석 결과가 6.0 krad다.”**
   - 현재 화면 값은 등록된 합성 이산 table이다. 실제 SPENVIS environment contract와 과학 교차검산이 없다.

4. **“EX-100의 TID·SEU가 VALID이며 RDM 4.1을 만족했다.”**
   - TID·SEU는 합성 fixture다. 실제 성적서 원문·권리·시험 조건·exact identity 검토가 없다.

5. **“SEC-DED ECC를 켜면 실제 오류가 79% 감소한다.”**
   - 화면은 합성 정책 비교다. 실제 ECC 구현 성능이나 실제 부품 완화 효과가 아니다.

6. **“False PASS 0건”, “19개 적대적 테스트를 통과했다.”**
   - “고정된 합성 평가 세트의 평가 가능 항목에서”라는 분모가 필요하다. 공격과 재현성 control, `NOT_EVALUATED` 항목을 구분해야 한다.

7. **“실시간 라이브 시연”, “실시간 로그”, “완벽히 실행됐다.”**
   - 로컬 HTML은 새 GCP 실행을 트리거하지 않는다. H05에서 실행·검증된 합성 snapshot을 재생한다.
   - 권장: “독립 검증된 H05 합성 GCP execution snapshot을 재생하겠습니다.”

8. **“0.013072에서 0.013073으로 1비트가 변조됐다.”**
   - 숫자값 mutation은 확인할 수 있으나 직렬화된 실제 바이트에서 정확히 한 비트만 바뀌었다는 증거는 아니다.

9. **“1,000회 Monte Carlo에서 bit-level 오차 0을 입증했다.”**
   - 현재 감사 대상과 저장소에서 해당 검증 증거를 확인하지 못했다.

10. **“`ifGenerationMatch=0`으로 파이프라인 전 과정의 위변조를 물리적으로 원천 차단했다.”**
    - create-only 저장은 특정 객체 overwrite를 막는 통제다. 입력 출처, 권한 오용, 새 객체 생성, 전 구간 변조를 모두 제거하지 않는다.

## 3. 가장 설득력이 약한 슬라이드·대본 구간 5개

### 1) 대본 전체 슬라이드 매핑

HTML은 13장이지만 대본은 11장이다. HTML의 `03 · COTS 비교`, `04 · 차폐 이해`가 대본에서 빠져 대본의 “03 입력”부터 실제 화면보다 두 장씩 밀린다. 실제 발표 동선과 제한 시간 서사에 가장 직접적인 위험이다.

### 2) 01 문제 정의의 산업 통계

근거 체인 단절이라는 핵심 문제는 강하지만, COTS 80~90%, 조기 실패 40~50%, 원인 86%를 한꺼번에 확정적으로 말하면 출처·모집단·원인 분류 질문에 취약하다.

### 3) 환경·부품·ECC 구간

합성 table과 fixture를 실제 물리 모델 실행 및 실제 부품 시험 결과처럼 말한다. 제품이 요구하는 증거 규율을 발표 문구가 위반하는 구간이다.

### 4) GCP 라이브 시연 구간

구조와 오류 격리 시각화는 강하지만, 저장된 H05 snapshot을 실시간 실행이라고 소개한다. 정확히 설명하면 강점이지만 과장하면 전체 데모의 신뢰가 흔들린다.

### 5) Q8·Q9 방어 답변

1,000회 Monte Carlo, Triple-Lock, 물리적 원천 차단, 모든 수치가 공인 DB 기반이라는 문구는 현재 증거 범위를 가장 크게 넘는다. 전문 심사위원이 한 가지 근거만 요청해도 답변이 붕괴할 수 있다.

## 4. 예상 질문 10개와 좋은 답변 기준

1. **왜 단일 서비스가 아니라 Multi-Agent인가?**
   - 환경·부품·독립 판정의 책임, 입력·출력 contract, 권한과 실패 전파 경계를 설명한다.
   - 핵심이 “AI 여러 개”가 아니라 역할·권한 분리임을 밝힌다.

2. **세 Agent는 무엇을 주고받는가?**
   - 각 Agent의 입력 schema, 출력 status, hash binding, 다음 호출 차단 조건을 한 문장씩 제시한다.

3. **왜 Cloud Run, Workflows, Storage를 선택했는가?**
   - Cloud Run은 역할별 배포·IAM 격리, Workflows는 순서·오류 trap, Storage는 결과 receipt와 create-only 보존이라는 선택 이유를 제시한다.

4. **현재 화면이 지금 GCP를 호출하는가?**
   - “아니다. H05에서 실제 수행하고 독립 확인한 합성 execution snapshot을 로컬에서 재생한다”고 즉답한다.

5. **LLM은 실제로 어디에 사용되는가?**
   - 핵심 수치·판정은 결정론적 코드라고 설명한다. 향후 AI 추출값은 `CANDIDATE`이며 엔지니어 승인 전 판정에서 제외된다고 답한다.

6. **현재 실제로 검증된 것은 어디까지인가?**
   - H05 합성 GCP 배포·역할 격리·입력 무결성 공격 차단·HOLD 전달만 검증됐다고 범위를 닫는다.
   - 실제 환경 contract, exact-part 성적서, 권리, 과학 적합성은 0건이며 실제 assurance는 `HOLD`라고 밝힌다.

7. **False PASS 0의 분모는 무엇인가?**
   - 고정 manifest 범위, 공격과 control 구분, `NOT_EVALUATED` 제외 원칙을 설명한다. 미래의 모든 입력에 대한 무오류 보장은 아니라고 덧붙인다.

8. **HOLD만 내는 시스템의 사업 가치는 무엇인가?**
   - 승인을 대신하는 것이 아니라 누락 근거, 재시험 필요 항목, 변경 영향의 우선순위를 앞당긴다고 답한다.
   - 실제 시간 절감은 파일럿 검증 전이라고 구분한다.

9. **기존 Excel·PLM·NASA/ESA 도구와 무엇이 다른가?**
   - 기존 도구를 폄하하지 않는다. 계산·문서 저장을 대체하지 않고, 출력의 identity·조건·권리·변경 영향을 기계 검증하는 실행 계층이라고 답한다.

10. **1인 프로젝트에서 역할 간 시너지는 어떻게 구현했는가?**
    - 사람 수가 아니라 책임 분리, Agent별 contract, 독립 감사, 실패 격리, Control Tower 검증 절차로 답한다.
    - 각 역할을 독립 담당자가 인수할 수 있는 경계가 있다는 점을 제시한다.

## 6. 최종 합격 가능성 판단

현재 HTML과 아키텍처는 **합격권**이다. Multi-Agent 역할 분리, GCP 실행 증거, Fail-Closed 설계, 인터랙티브 데모는 교육 프로그램 결과물로서 분명한 강점이다. 1인 수행과 리허설 여부는 본 판단에서 불이익을 주지 않았다.

다만 현재 대본 그대로라면 **조건부 합격권**이다. 핵심 철학은 “근거 없는 판단을 하지 않는다”인데 발표자가 실계산·실시간·완전 검증을 과장하면 가장 중요한 신뢰성 항목에서 자기모순이 발생한다. P0를 반영하면 안정적인 합격권과 상위 평가 가능성이 있다. 반영하지 않으면 전문 심사위원의 증거 범위 질문에서 큰 감점이 예상된다.
