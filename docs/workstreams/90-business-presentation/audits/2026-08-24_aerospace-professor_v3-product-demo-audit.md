## 4. 개선 우선순위

### P0 — 제출 전 반드시 해결

1. **실제 TI 후보의 4번 관문을 수정해야 합니다.** 승인 BOM exact-part target이 0건이면 `대상 일치 PASS`가 아니라 `승인 target 없음 · NOT_EVALUATED/HOLD`여야 합니다. 주문형번 추출 성공과 target match는 다른 사실입니다.
2. 마지막 UI 변경 이후 전체 시연 순서에 대한 브라우저 회귀와 실제 낭독·클릭 리허설을 수행해야 합니다. 목표는 7분 이내이며, 화면 전환 실패와 새로고침 복구까지 확인해야 합니다.
3. Product의 “다섯 관문/여섯 관문” 불일치를 제거하고, 실제 후보에는 `UNAPPROVED_CANDIDATE · NOT FOR DECISION`을 관문 옆에서도 즉시 보이게 해야 합니다.

### P1 — 큰 감점을 막는 보완

1. `Mission VALID`는 “환경 입력 형식·provenance 처리 성공”으로 제한하십시오. 실제 입자환경·선량의 과학적 정확도 검증이 아닙니다.
2. 실제 TI 후보는 “exact part”가 아니라 **orderable part-number candidate**로 부르는 것이 안전합니다. 승인 BOM 대조, die/process/lot, 시험 대상 적용성은 미확정입니다.
3. TID 언급 추출과 TID 시험 적용성 검토를 구분하고, SEU·SEL·SEB·SEGR coverage가 해결되지 않았음을 시연 화면에서 한 줄로 유지하십시오.

### P2 — 설득력 강화

1. 최초 구매자와 파일럿 책임자를 구체화하십시오. 예: 위성 전장 설계 책임자, parts assurance/RHA 담당자, 공급망 품질 담당자.
2. Slide 10에서는 버튼과 하단 보안 문구를 모두 읽지 말고 정상 기록과 공격 차단 하나만 강조하십시오.
3. Product Demo가 열리지 않을 때 사용할 고정 fallback 화면을 준비하십시오. 단, fallback도 저장 기록 또는 화면 캡처일 뿐 live 실행이라고 말하면 안 됩니다.

## 6. 시연 실패 위험과 fallback

주요 위험은 다음과 같습니다.

- 마지막 UI 변경 후 정식 브라우저 회귀가 완료되지 않았습니다.
- Product가 최소 폭 1080px를 요구하므로 프로젝터 해상도나 브라우저 확대율에 따라 글자가 잘릴 수 있습니다.
- 95초 안에 합성 자료 로드, 세 후보 확인, 실제 후보 재로드, TI 선택, Step 3 변경까지 수행하는 것은 클릭 실수에 취약합니다.
- 상태를 여러 번 오가는 과정에서 이전 선택과 활성 단계가 관객에게 혼동을 줄 수 있습니다.

권장 fallback은 Slide 11에서 멈추고 다음처럼 설명하는 것입니다.

> “시연 화면은 파일 무결성, 권리, 대상 일치, 시험 적용성을 순서대로 검사합니다. 실제 TI 후보에서는 주문형번과 TID 표지만 확인됐고, 승인 BOM·시험 조건·SEE coverage가 없어 판단에는 사용하지 않고 HOLD했습니다.”

GCP 역시 Slide 10의 저장 execution ID와 HOLD 화면만 사용하고, 새 Workflow를 실행했다고 말하지 않아야 합니다.

## 7. 예상 심사 질문 5개와 짧은 모범답

### 1. `5962L1420901VXC`를 찾았는데 왜 exact-part 증거가 아닙니까?

> 주문형번 후보를 원문에서 찾은 것뿐입니다. 승인 BOM의 target, 제조 공정·다이·로트, 시험 대상과 조건의 동일성이 확인되지 않았으므로 exact-match나 임무 적합성으로 승격하지 않습니다.

### 2. Mission Agent가 VALID라면 실제 환경 계산도 검증된 것 아닙니까?

> 아닙니다. VALID는 해당 합성 저장 실행에서 입력 형식·결속·처리 경로가 정상이라는 뜻입니다. 실제 environment contract와 독립 과학 교차검산은 0건이므로 최종 판단은 HOLD입니다.

### 3. ECC로 잔여 오류가 줄었으면 부품을 쓸 수 있지 않습니까?

> 아닙니다. 현재 값은 합성 SEU 비교입니다. 실제 ECC 구현·scrub 주기·메모리 구조 검증과 SEL·SEB·SEGR 같은 파괴성 SEE 근거를 대신하지 않습니다.

### 4. 왜 하나의 서비스가 아니라 Multi-Agent가 필요합니까?

> 숫자를 더 많이 생성하기 위해서가 아니라 환경, exact-part, 최종 blocking gap의 책임과 실패 경계를 분리하기 위해서입니다. 한 단계가 실패하면 다음 단계가 빈칸을 추측하지 않고 중단됩니다.

### 5. 고객이 실제로 얻는 경제적 효과가 있습니까?

> 아직 절감액이나 ROI를 주장하지 않습니다. 파일럿에서 case당 active review time, trace completeness, 보완 return rate를 측정해 반복 탐색과 재검토가 실제로 줄어드는지 검증하겠습니다.

## 8. 최종 판단

# **CONDITIONAL GO**

발표의 핵심 철학, GCP 저장 기록의 경계, 합성/실제 구분, 최종 HOLD는 상당히 잘 정리되어 있습니다. 그러나 승인 BOM 0건인 실제 후보가 `대상 일치`를 PASS하는 현재 상태는 이 발표가 가장 중요하게 내세우는 exact identity 원칙과 직접 충돌합니다.

따라서 다음 두 조건을 만족하면 제출 가능하다고 판단합니다.

1. 실제 후보의 4번 관문을 `후보 식별`과 `승인 target exact-match`로 분리하고, 현재 상태를 NOT_EVALUATED/HOLD로 표시할 것.
2. 수정 후 실제 브라우저 회귀와 7분 클릭 리허설을 완료할 것.

이 두 조건을 충족하지 못한 채 현재 화면 그대로 제출한다면, 우주항공 심사위원에게는 “HOLD를 잘 말하지만 실제 제품은 exact-match를 낙관적으로 PASS한다”는 치명적인 반론을 받을 가능성이 큽니다.
