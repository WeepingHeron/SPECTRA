## 2. 비전문가가 30초 안에 이해하는 한 문장

> **SPECTRA는 위성 부품을 쓰기 전에 흩어진 임무·BOM·시험 문서를 하나의 검사 과정으로 연결하고, 근거가 틀리거나 부족하면 자동 승인하지 않고 어디서 막혔으며 무엇을 보완해야 하는지 알려주는 검토 플랫폼입니다.**

현재 대본의 “Evidence Chain”보다 위 문장이 일반 스타트업 심사위원에게 빠르게 전달된다. 방사선 계산보다 고객이 받는 결과인 **차단 위치와 다음 행동**을 먼저 말하는 것이 좋다.

## 3. 발표자료–대본–시연 연결성

### 연결이 잘 된 부분

**문제에서 제품 동작까지 논리적이다.**

1. Deck 01–03: 근거가 여러 파일에 흩어져 사람이 다시 연결한다.
2. Deck 05–08: 잘못된 identity, 범위 밖 수치, 근거 결측을 HOLD한다.
3. Deck 09–10: 결정론적 Core와 세 Agent가 계산·증거·판정 책임을 분리한다.
4. Product Demo: 파일을 6개 관문으로 검사하고 변경 시 영향받은 관문부터 다시 연다.
5. Closing: 자동 승인이나 시험 대체가 아니라 추적 가능한 검토 경로라고 결론 낸다.

특히 실제 TI 후보가 exact part까지 확인된 뒤 적용성에서 멈추고 “사람이 시험 조건과 BOM 적용성을 검토한다”고 안내하는 장면은 기술 원칙을 제품 가치로 바꾼다.

### 연결이 약한 부분

**Slide 11은 ‘향후 로드맵’인데, 대본은 이를 ‘현재 실제 제품 흐름’으로 전환한다.** Document AI와 변경 영향 분석이 향후 기능인지 현재 기능인지 비전문가가 혼동할 수 있다. 현재 구현된 것은 로컬 추출 receipt 검토와 합성 변경 영향 시연이고, 실제 승인 pipeline은 아니다.

**Product Demo 상단의 `ACTUAL REVIEW · HOLD`는 합성 control을 볼 때도 유지된다.** 본문에는 합성이라고 표시되지만 첫인상은 실제 검토처럼 보일 수 있다. `SYNTHETIC CONTROL`과 `ACTUAL CANDIDATE` 상태가 선택에 따라 바뀌어야 화면과 대본이 완전히 일치한다.

**대본은 실제 PDF 추출과 현재 시연 동작을 한 문장에 섞는다.** Product Demo에서 즉석으로 328쪽 PDF를 분석하는 것이 아니라, 앞서 생성된 로컬 extraction receipt를 읽어 후보와 차단 상태를 보여준다. 발표에서도 “사전 로컬 추출 receipt”라고 구분해야 한다.

## 4. 개선 우선순위

### P0 — 제출 조건

1. **최종 파일 기준 전체 브라우저 회귀를 완료한다.** venue 해상도에서 합성 3종, 실제 후보 3종, Step 3 세 변경, 초기화, fetch fallback, overflow와 console error를 확인해야 한다.
2. **7분 전체를 실제 클릭으로 실측한다.** 목표는 계산상 6:30이 아니라, 실측 6:40 이내다. 실패 시 Product Demo를 한 장면으로 축소한다.
3. **구매자와 첫 pilot을 한 문장으로 명시한다.** 예: “첫 pilot은 위성 개발사의 부품/RHA 검토 담당자가 사용하고, 기술 승인자와 품질·프로젝트 예산 소유자를 함께 검증합니다.” 검증된 고객처럼 말해서는 안 된다.

### P1 — 신뢰와 제품 이해도

1. Product Demo 상단 상태를 `SYNTHETIC CONTROL`과 `ACTUAL CANDIDATE · NOT FOR DECISION`으로 동적으로 분리한다.
2. “실제 PDF를 시연에서 분석한다”가 아니라 “실제 PDF에서 사전 추출한 후보 receipt를 검토한다”고 표현을 맞춘다.
3. Slide 11에서 현재 구현·합성 시연·향후 확장을 시각적으로 분리한다.

### P2 — 전달 밀도

1. 기술 스택 슬라이드는 Python·NumPy·SciPy보다 `결정론적 계산 / 증거 결속 / 역할 분리 / 공격 검증` 네 결과만 말한다.
2. Product Demo의 영어 상태명과 부가 라벨을 줄이고 “통과·차단·다음 행동”을 가장 크게 유지한다.
3. 실제 pilot 이후에만 active review time, trace completeness, return rate의 baseline과 변화를 제시한다.

## 5. 7분 안에서의 선택

### 반드시 자를 내용

**Product Demo의 합성 정상·변조·부품 불일치 3종 전체 순회**를 자른다.

세 후보의 차이는 탭에 이미 “끝까지 통과 / 2번 차단 / 4번 차단”으로 표시된다. 발표에서는 변조 후보 하나만 실행해 fail-closed를 보여주고 나머지는 화면을 가리키며 한 문장으로 설명하면 된다.

### 반드시 남길 장면

**실제 TI PDF 추출 후보가 5번 적용성 관문에서 멈추는 장면**을 남긴다.

이 장면 하나에 다음이 모두 들어 있다.

- 실제 문서 후보를 다룰 수 있음
- exact part와 제조사를 찾음
- AI 추출을 승인값으로 쓰지 않음
- TID 언급과 임무 적용성을 구분함
- 파괴성 SEE 근거가 없으면 HOLD함
- 다음 사람 검토 행동을 제시함

일반 스타트업 심사위원에게는 기술 스택보다 이 장면이 제품의 차별성을 더 잘 설명한다.

## 6. 시연 실패 위험과 fallback

| 위험 | 현재 판단 | Fallback |
|---|---|---|
| 새 창 또는 로컬 asset 로딩 실패 | 내장 데이터 fallback은 있지만 전체 회귀 전 | Product tab을 발표 전에 미리 열어 Step 1까지 로딩하고 네트워크 링크는 클릭하지 않는다. |
| 95초 내 조작 실패 | **높음** | 합성 변조 1건 → 실제 TI 후보 1건 → ECC 재검사 1건으로 고정한다. |
| 클릭 순서 혼동 | 중간 | 화면별 클릭 수를 1–2회로 제한하고 실제 후보 3건을 모두 순회하지 않는다. |
| Product 페이지 자체 오류 | 중간 | Deck Slide 11에 머물러 “변조는 2번, 다른 부품은 4번, 실제 TI 후보는 5번에서 멈추며 모두 HOLD”라고 15초 안에 설명한다. |
| GCP Console 연결 실패 | 낮음 | Slide 10 자체에 저장 실행 ID와 결과가 있으므로 외부 Console을 열지 않는다. |
| 작은 해상도·배율 문제 | 중간 | Product는 `min-width:1080px`이므로 발표 장치의 실제 해상도와 브라우저 배율 100%를 사전 고정한다. |

현재 세 파일 안에는 Product 페이지 전체가 실패했을 때 사용할 전용 정적 fallback 화면이 없다. 최종 회귀가 실패한다면 live Product Demo를 빼고 Slide 11 설명으로 전환하는 편이 안전하다.

## 7. 예상 심사 질문 5개와 짧은 모범답

### Q1. 누가 이 제품에 돈을 냅니까?

> 아직 확인된 구매자와 가격은 없습니다. 첫 pilot에서는 위성 개발사의 부품·RHA 검토 담당자를 사용자로, 기술 승인자와 품질·프로젝트 예산 책임자를 구매 의사결정자로 나눠 검증하겠습니다.

### Q2. 엑셀이나 문서관리 시스템과 무엇이 다릅니까?

> 파일을 보관하는 데서 끝나지 않고, 환경·부품·시험·권리의 연결이 깨진 위치와 다시 검토할 시작점을 기계적으로 표시합니다. 근거가 없으면 빈칸을 채우지 않고 HOLD합니다.

### Q3. 왜 Multi-Agent가 필요합니까?

> 답을 여러 개 만들기 위해서가 아니라 책임을 나누기 위해서입니다. Mission은 환경 출처, Parts는 exact identity와 시험 범위, Assurance는 앞선 결과와 HOLD 조건을 독립 대조하며 실패하면 후속 호출을 중단합니다.

### Q4. 실제 데이터를 분석한 결과입니까?

> 실제 SPENVIS와 TI 문서 후보에서 hash와 식별 후보를 추출했지만 승인값으로 쓰지 않았습니다. 권리, 승인 BOM, 시험 조건, 임무 적용성과 SEE coverage가 닫히지 않아 최종 판단은 HOLD입니다.

### Q5. 얼마나 비용이나 시간을 줄입니까?

> 아직 측정하지 않았기 때문에 절감률을 주장하지 않습니다. pilot에서 case당 active review time, trace completeness, 보완 return rate를 전후 비교해 반복 탐색과 재검토가 실제로 줄어드는지 검증하겠습니다.

## 8. 최종 제출 판단

# CONDITIONAL GO

기술적 사실 경계와 제품 논리는 제출 가능한 수준이다. 실제 environment contract 0건, 승인 BOM exact-part evidence 0건, 실제 후보 판단 미사용, 최종 assurance `HOLD`도 세 파일에서 일관되게 유지된다.

다만 다음 두 조건을 충족하기 전에는 완전한 `GO`로 보지 않는다.

1. 마지막 UI 변경이 포함된 정확한 snapshot으로 전체 브라우저 회귀를 통과할 것.
2. 축소된 시연 동선으로 발표+시연을 실측해 7분 안에 끝낼 것.

이 발표의 승부처는 더 많은 기술을 보여주는 것이 아니다. **실제 후보를 읽을 수 있지만 근거가 부족하면 판단에 쓰지 않고, 담당자에게 다음 행동을 돌려주는 제품**이라는 점을 한 장면으로 이해시키는 것이다.
