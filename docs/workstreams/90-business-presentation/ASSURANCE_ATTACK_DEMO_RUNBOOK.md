# SPECTRA 초심자용 결과 전달 오류 테스트 Runbook

## 문서 계약

- package: `90-cover-and-product-clarity-narrative-v1`
- submission: `H10`
- 기준선: Workstream 90 H09 `CHANGES_REQUESTED`; Workstream 80 H15 `READY_FOR_REVIEW`
- UI 정렬 목표: Workstream 80 H15의 차폐·TID·SEU·ECC 계산과 Product 04 결과 전달 layer 구분
- 상태 상한: `READY_FOR_REVIEW`
- 시간: `PLANNED 70초`. 사람 낭독·클릭·탭 전환은 아직 `MEASURED`하지 않았다.
- 모든 값은 `SYNTHETIC`이며 실제 방사선 계산의 과학 정확성·GCP 보안·전자서명·공격자 신원이나 권한을 검증하는 시연이 아니다.

## 가장 먼저 전달할 한 문장

> 화면에 들어온 숫자가 정상 계산 당시 기록과 다르면, SPECTRA는 그 숫자를 믿고 보여 주지 않습니다.

## 전체 발표에서 들어가는 위치

`임무·BOM → 차폐·TID·SEU·ECC → 근거 연결·범위 밖 차단 → 보증 판단(HOLD) → 결과 전달 오류 테스트 → 제품 가치·차별점 → 한계·다음 단계·마무리`

연결 문장:

> 앞에서는 차폐와 ECC가 바꾸는 값, 근거 연결과 `HOLD`를 확인했습니다. 지금 보는 숫자 변경 감지는 계산이 끝난 뒤 그 결과가 화면까지 그대로 전달됐는지를 확인하는 별도 안전장치입니다.

이 장면은 방사선 수치를 새로 계산하는 장면이 아니라 네 번째 안전장치인 `전달된 숫자가 다름 → 숫자 숨김`을 확인하는 `결과 전달 오류 테스트`, 즉 `오류 주입 테스트`다. Product 화면명은 `숫자 변경 감지`를 그대로 사용한다.

시간 산술: `20 + 20 + 20 + 10 = 70초`. 시간에는 화면 지시·클릭·관객 확인 여유가 포함되며 사람 리허설 전까지 `PLANNED`다.

## 단계별 인과관계

1. 계산 직후 저장한 원래 기록이 있다.
2. 화면에 들어오기 전 일부러 바꾼 테스트용 값이 있다.
3. 둘이 다르므로 숫자를 숨기고 판단을 보류한다.

## 기술 상세 — Q&A에서만 사용

- **preimage:** 결과의 데이터 지문을 만들 때 사용한 정상 계산 당시의 원문 기록이다.
- **consumer:** 결과 파일을 읽어 화면에 표시할지 결정하는 Product의 읽기 경로다.
- **sibling anchor:** result ID와 input/output hash를 별도로 연결해 둔 무결성 보조 기록이다.
- **hash/SHA-256:** bytes가 같은지 비교하는 데이터 지문이다. 과학적 진실성·자료 권리·작성자 신원은 증명하지 않는다.
- **reason code:** 기술 진단용 `RUNTIME_PREIMAGE_VALUE_MISMATCH`다. 주 대본에서는 “원래 기록과 불일치”라고 말한다.

### Q. 왜 데이터 지문 문자열만 비교하지 않나요? — `PLANNED 20초`

“같은 지문 문자열을 여러 위치에 복사해 둔 것만으로는 화면의 숫자가 그 지문을 만들 때 사용한 내용과 같은지 알 수 없습니다. 그래서 지문과 원래 기록을 확인하고, 원래 기록의 내용도 들어온 결과와 같은지 대조합니다. 하나라도 다르면 해당 결과를 숨기고 판단을 보류합니다.”

## 발표 현장 fallback — `PLANNED 30초`

독립 `숫자 변경 감지` 화면이 열리지 않거나 탭 전환에 실패하면, 정상 제품 화면의 `계산 직후 기록` 카드만 가리키고 다음과 같이 말한다.

> “정상 합성 계산 직후 기록이 있고, 원본을 보존한 사본에서 화면에 들어갈 숫자만 잘못 바뀌었다고 가정하겠습니다. 두 기록이 다르면 SPECTRA는 어느 쪽을 믿을지 추측하지 않고 숫자를 숨긴 뒤 판단 보류로 닫습니다. 지금은 실패한 화면을 꾸며 내지 않고 검증된 원리만 설명드렸습니다.”

## 말하면 안 되는 주장

- `999`가 실제 서비스 중단 시간 또는 새 계산 결과라는 주장
- 60이 자동으로 정답이라고 복구·채택했다는 주장
- 해커 침입, 공격자 신원·권한, 전자서명 또는 프로젝트 전체 무결성을 검증했다는 주장
- 실제 GCP 보안이나 방사선 계산의 과학 정확성을 검증했다는 주장
- 실제 environment·parts evidence가 있거나 최종 assurance가 PASS라는 주장

- 실제 control: `테스트용 숫자 바꾸기 → 두 기록 비교하기 → 정상 상태로 되돌리기`
- 실제 카드: `01 · 계산 직후 기록 → 02 · 화면에 들어온 값 → 03 · 처리 결과`
- 실제 처리 문구: `서로 다름 → 숫자 숨김 → 판단 보류(HOLD)`
- 실제 맥락 label: `신뢰성 안전장치 4/4 · 전달 중 숫자 변경`
- 실제 계산/전달 layer 문장: `계산·검증은 결과를 만들고, 숫자 변경 감지는 그 결과가 Product로 전달되는 과정을 지킵니다.`
- 위 항목은 2026-08-21 H15 `READY_FOR_REVIEW` handoff와 current source에서 exact 대조했다. H15 actual browser는 `NOT_EVALUATED`이며 Control Tower `VERIFIED` 전이다.

`CONTRACT_CHANGE_REQUEST`: H15가 기록한 발표 HTML residual `0.0063072`와 Product current residual `0.013072`의 결과 계층 차이를 인수한다. 이 runbook은 해당 수치를 방사선 성능으로 비교하지 않고 결과 전달 불일치 장면만 다룬다.
